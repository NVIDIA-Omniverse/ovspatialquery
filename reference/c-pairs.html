Pair Discovery#

This page is generated from ovspatialquery_pairs.h, the installed header that is the contract. For the model, refer to Pair Discovery.

AABB pair discovery: stateless snapshots and forward-only reporters.

This header is the stateful half of ovspatialquery. Every function in it is experimental and may change in any minor release, because pair discovery is still shaped by its first callers. It reads populations published through the core and shares its instance, targets, ordinals, object IDs, status codes, budgets, and operation lifecycle.

A pair snapshot is a synchronous, stateless set of overlapping pairs between two independently selected versions. A pair reporter keeps one accepted baseline of pairs and, on each explicit forward advance, reports which pairs entered and which exited. Both test world AABBs with one predicate on every axis, first_min[i] <= second_max[i] + tolerance && second_min[i] <= first_max[i] + tolerance, and neither claims exact contact.

Typical reporter flow (status checks omitted):

ovspatialquery_create_pair_reporter(instance, &desc, &reporter);
advance = ovspatialquery_enqueue_pair_reporter_advance(
    instance, reporter, &endpoints, &reservation);   // (20,100): every pair entered
ovspatialquery_wait_op(instance, advance.op_id, timeout, &wait_result);
ovspatialquery_fetch_pair_reporter(instance, advance.op_id, &report);
ovspatialquery_destroy_op(instance, &advance.op_id);
// later, after robots publishes 104: advance to (20,104) reports entered and exited
ovspatialquery_destroy_pair_reporter(instance, reporter);

Two targets in the same population must select one ordinal (ORDINAL_MISMATCH otherwise). Distinct targets keep their roles, so two overlapping views can produce (A,B) and (B,A) but never (A,A).

Nonnegative margin used by the defined world-AABB predicate.

A snapshot is one stateless AABB-pair test over selected immutable versions.

Multi-rate populations require independent selections: a program can compare static ground at ordinal 20 with moving robots at ordinal 104. Numeric ordinal equality has no cross-population meaning. If both targets have the same parent population, they must select the same ordinal; otherwise the call returns ORDINAL_MISMATCH.

An object passes one role’s filter when that role’s query bits are zero or intersect the object’s participation bits. For distinct targets, first and second preserve their descriptor roles. Distinct overlapping views can therefore produce both (A,B) and (B,A), but never (A,A). When both target, ordinal, and query-bit selections are identical, pairs are unordered: self-pairs are excluded and each {A,B} pair appears once with the smaller object ID in first.

Two admitted objects form a pair exactly when, for every axis i:

first_min[i] <= second_max[i] + contact_tolerance &&
second_min[i] <= first_max[i] + contact_tolerance

These are published world AABBs, so the predicate makes no exact-geometry overlap claim. Acceleration layout and traversal policy are implementation details.

struct ovspatialquery_pair_reporter_advance_t#

One advance of a reporter. A CPU reporter requires zero cuda_sync.has_stream and cuda_sync.wait_event and endpoints that name completed publications. A CUDA reporter queues the advance on the supplied cuda_sync.stream, the legacy default stream 0 included, after a nonzero wait_event, so a consumer the caller queues on that stream runs after it; without a stream (has_stream 0) the advance runs on the reporter’s own stream, and the consumer then waits on result_ready. A CUDA reporter may also select an admitted device-prepared publication on its device with ADMITTED_EXACT: the advance is ordered after the publication on the device, and if the publication fails the advance completes with OPERATION_FAILED, writes the FAILED outcome to its device counts and preserves the baseline.

struct ovspatialquery_pair_reporter_reservation_t#

Immutable reservation facts returned by a successful reporter enqueue.

The library writes this caller-owned value before return and never retains or modifies it. The selected ordinals, typed outcome, accepted active count, and entered/exited stored counts are completed facts returned on the host only by fetch. A CUDA reporter’s reservation also describes the device storage the advance writes, shaped by the capacity like a batch reservation: a consumer queued behind the advance on cuda_sync.stream, or made to wait on result_ready, reads the same bytes fetch later describes without a host round trip. A CPU reporter’s results stay fetch-only and its three descriptors are absent (shape == NULL).

Computes a stateless AABB-pair set between two selected immutable versions. inout_pairs->capacity is the only output bound. Additional pairs set out_result->truncated; no second descriptor capacity exists. Use this for an arbitrary instantaneous comparison. It creates no accepted baseline.

ovspatialquery_result_t ovspatialquery_create_pair_reporter(
ovspatialquery_instance_handle_t instance,
const ovspatialquery_pair_reporter_desc_t *desc,
ovspatialquery_pair_reporter_handle_t *out_reporter
)#

Creates an empty-baseline, forward-only AABB-pair reporter.

Typical sequence: create; advance to (100,100), which reports all current pairs in entered_pairs; advance to (104,104), which reports only endpoint set differences; fetch and consume; destroy each operation. Advancing to (102,102) after 104 fails with BACKWARD_ORDINAL. Destroy and recreate the reporter to start a new baseline after a discontinuity. The reporter owns only the accepted pair set and selected ordinals. Ordinal selections made by other queries or plans never affect a reporter; its baseline moves only through its own advance call. BVH, SAP, rebuild, incremental-update, and temporal-coherence choices are implementation details.

The reporter uses the snapshot predicate, target-role, same-target, self-pair, overlapping-view, and participation-bit rules. If its targets share one parent population, each advance must select one common ordinal.

ovspatialquery_enqueue_result_t ovspatialquery_enqueue_pair_reporter_advance(
ovspatialquery_instance_handle_t instance,
ovspatialquery_pair_reporter_handle_t reporter,
const ovspatialquery_pair_reporter_advance_t *advance,
ovspatialquery_pair_reporter_reservation_t *out_reservation
)#

Admits one forward advance. Both resolved ordinals must be nondecreasing and at least one must increase. A jump compares only the accepted baseline with the new endpoint pair set; it does not replay transient pairs. The first successful advance compares against an empty set and reports every current pair as entered.

The first advance has no accepted endpoint ordinals to compare. For every later advance, both selections are resolved atomically before admission. If either resolved ordinal is older than its accepted ordinal, the call returns BACKWARD_ORDINAL. Otherwise, if both equal their accepted ordinals, the call returns STALE_ORDINAL. Otherwise the call can be admitted because at least one endpoint advanced. Both rejections issue no operation ID, reserve no result slot, and preserve the baseline and private accepted-advance count.

A sensor loop can poll both endpoints with HEAD. When it polls faster than publication, STALE_ORDINAL means it can retry the same HEAD request after a later publication. An exact equal/equal request remains stale until the caller selects a later ordinal. NOT_READY is reserved for a target that has no selectable version; it does not report lack of progress.

A completed capacity outcome is not a partial advance. ACTIVE_CAPACITY and DELTA_CAPACITY return empty delta views and preserve the previous baseline. Other failures also preserve the baseline.

Successful admission writes only immutable reservation facts. The library does not retain or modify out_reservation after return. Typed fetch returns the selected ordinals, outcome, accepted active count, and exact entered and exited counts. It is repeatable and non-consuming; it returns NOT_READY while pending and OPERATION_FAILED after terminal failure, preserving its output.

A CPU reporter has one advance pending at a time (BUSY otherwise). A CUDA reporter’s advance is enqueued on the device at admission (cuda_sync), may select admitted device-prepared publications on its device, and retires through ovspatialquery_destroy_op_after_cuda() once its consumers are done; see ovspatialquery_pair_reporter_advance_t. Up to result_slot_count of its advances may be pending at once (RESULT_CAPACITY beyond): while any is pending, BACKWARD_ORDINAL and STALE_ORDINAL are judged against the newest admitted endpoints, the advances compare on the device in admission order, and one admitted behind a capacity outcome or a failure compares with the preserved baseline, as the jump rule above allows. Outcomes are published in the same order.

ovspatialquery_result_t ovspatialquery_grow_pair_reporter_capacity(
ovspatialquery_instance_handle_t instance,
ovspatialquery_pair_reporter_handle_t reporter,
uint64_t active_pair_capacity,
uint64_t delta_pair_capacity
)#

Grows one idle reporter’s active and delta capacities atomically.

Both requested capacities must be at least their current values and at least one must grow. The call returns BUSY while any advance is live. It never changes filters, result-slot count, device, accepted ordinals, or the private baseline. All replacement storage is budgeted and prepared before either capacity changes. HOST_BUDGET, DEVICE_BUDGET, OUT_OF_MEMORY, or any other failure leaves both capacities and the baseline unchanged. Shrinking, reset, rebase, and snapshot seeding are intentionally not operations here.
