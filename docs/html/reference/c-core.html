Core API#

This page is generated from ovspatialquery.h, the installed header that is the contract. Every other header builds on this one. For the model behind it, refer to Concepts.

Backend-neutral spatial-query C interface.

The ovspatialquery library answers raycast, sphere/box-sweep, and overlap questions over geometry the caller publishes. This header is the scene-query core. Sources are companion headers (ovspatialquery_ovstage.h, the preferred one, and ovspatialquery_explicit.h), as is AABB pair discovery (ovspatialquery_pairs.h); none of them is required by this header.

Releases follow SemVer 2.0, and ovspatialquery_get_version() reports the library’s version. A patch release changes no declaration. While the major version is 0, a minor release may change any declaration or struct layout, so a caller rebuilds against each minor release. From 1.0, changing the layout of a public struct needs a major release; the interface grows by new entry points instead (a _v2 suffix when one replaces another), and the replaced declaration carries OVSPATIALQUERY_DEPRECATED for at least one minor release and is removed only in a major release. Experimental declarations, marked OVSPATIALQUERY_EXPERIMENTAL or with a comment that begins “Experimental:”, are outside that rule: they may change in any minor release. Device-prepared publications and everything they alone enable are experimental, and so is all of ovspatialquery_pairs.h. A comment paragraph that begins “Implementation note:” describes how this release behaves, to help a caller size and diagnose its use; it is not a promise and may change in any release.

An instance owns resource budgets and every object created through it. A population is one independently updated object set; each publication creates an immutable version identified by an ordinal. The newest version is the head, and the configured number of prior heads stay selectable. A view is a stable subset of one population. A query targets a population or view and selects its head or one retained ordinal, without copying the population or its acceleration data.

Typical flow (error handling omitted):

ovspatialquery_create_instance(&instance_desc, &instance);
ovspatialquery_create_ovstage_population(instance, &source, &population);
update = ovspatialquery_enqueue_ovstage_population_set(
    instance, population, ovstage_ordinal);
ovspatialquery_wait_op(instance, update.op_id, timeout, &wait_result);
ovspatialquery_raycast_closest_sync(instance, &ray, &hit);
ovspatialquery_destroy_op(instance, &update.op_id);

Rules that apply to every function unless its own comment says otherwise: functions return status by value; zero handles are invalid; a rejected call preserves its outputs; diagnostics are thread-local; and asynchronous work must reach an observed terminal state (through a wait, a status poll, or a terminal typed fetch) before its operation is destroyed. The caller owns coordinates, units, frames, tolerances, and ordinals, and a query performs no source I/O and no geometry preparation, except the one-time host copy an ON_DEVICE_HOST_READABLE version makes for its first CPU reader. Every resource is bounded by an explicit instance, population, or plan capacity.

Synchronous CPU queries return tagged records; CPU and CUDA batches return DLPack result columns. This header embeds DLTensor by value, so the DLPack C layout is part of the ovspatialquery ABI.

Handles and common scalar types#

Handles and operation IDs are distinct structs holding one uint64_t raw_id, as in the other Omniverse libraries, so passing one kind where another is expected fails to compile. Use raw_id only at numeric boundaries (hashing, logging, foreign bindings) and keep arguments and storage typed: compare with each type’s _equal and _is_valid functions in C, or with == and != in C++, where the types also order and hash by raw_id. The types distinguish kinds, not instances or lifetimes: a handle from another instance or a destroyed object is still a run-time INVALID_HANDLE. Copying a handle does not retain its object. A zero raw_id is invalid in every type. A process may load several copies of the library, each working independently; passing a handle or operation ID to a copy other than the one that returned it is undefined behavior and is not detected.

Population terms used throughout this header.

A population is one independently updated set of spatial objects. A publication creates an immutable state identified by a population-scoped ordinal. The head is the newest successfully published state; work still in progress is not the head. A retained ordinal is an older state that remains selectable by new queries. An admitted ordinal is a publication that has been accepted and is still being prepared; CUDA plan launches may select it when it is prepared on their device, and their work waits for it there. Admission selects and keeps one immutable state alive without copying the population or its acceleration data.

For example, one query can select retained ordinal 102 while another selects head ordinal 104 from the same population, and a CUDA overlap batch can be enqueued against admitted ordinal 105 before the publication of 105 has finished.

has_stream separates “no stream” from stream 0, the legacy default stream: 1 supplies stream, 0 supplies none and the library ignores stream, and any other value returns INVALID_ARGUMENT. enum ovspatialquery_preparation_t#

Where the library validates and prepares a publication’s version. The explicit and ovstage adapters both take it, and each states what its publications read on either side.

ON_HOST: the library prepares objects, bounds, and the tree on the host, so every reader works. ON_DEVICE: device kernels validate the publication’s poses and prepare the version on dynamic_execution.device, and its tables stay there; a CUDA plan reads them directly and nothing but a fixed-size status crosses to the host.

A version does not move between the two: an ON_DEVICE publication on a population whose head was prepared on the host returns NOT_SUPPORTED at admission, and so does an ON_HOST publication on a device-prepared head. Readers of a device-prepared version are CUDA overlap, raycast, and sweep plans with BOUNDS precision in any hit mode over the whole population, and CUDA pair reporters on that device over whole populations; an ANY hit is the hit CLOSEST would report. Exact CUDA plans and CPU readers need the version’s objects, which only an ON_DEVICE_HOST_READABLE publication supplies (NOT_SUPPORTED otherwise); views and CPU reporters return NOT_SUPPORTED. Those plans and reporters may select the version with ORDINAL_ADMITTED_EXACT before its publication completes, and up to the population’s pending_publication_capacity device-prepared updates may be pending at once, each based on the one admitted before it, so a producer publishes and queries every step without a host wait. The first complete set must complete before an update builds on it.

ON_DEVICE_HOST_READABLE prepares the version on the device exactly as ON_DEVICE does, and additionally lets CPU readers select it: the first synchronous query, CPU plan launch, or pair snapshot that selects the version downloads its poses and builds the host objects and tree, once, charged to the host budget at that reader’s admission (HOST_BUDGET when it does not fit, and the reader is refused) and released with the version. A pure GPU pipeline that never selects the version from the CPU pays nothing. Plain ON_DEVICE keeps returning NOT_SUPPORTED to CPU readers. Views and CPU pair reporters stay NOT_SUPPORTED for either.

struct ovspatialquery_geometry_ref_t#

Identifies one exact immutable geometry definition within an instance.

The source adapter assigns value; zero is invalid. Callers compare the complete structure for equality but do not interpret value. References are instance-scoped and comparable across populations in that instance. Equal references name the same adapter-recognized immutable definition. Unequal references can still contain equal geometry bytes. References from separate instances are not comparable. Values are not reused during instance lifetime. The adapters split the value space so that they never contend for a value: explicit registration takes caller values from 1 to 2^63 - 1, and the ovstage adapter assigns values from 2^63 up. struct ovspatialquery_input_array_t#

One DLPack input column with an independent data-lifetime choice.

The library copies tensor metadata, shape, and strides during admission; ownership governs only tensor.data. The caller keeps a borrowed array unchanged until terminal completion and may change a copied CPU array as soon as admission succeeds. For copied CUDA data, the library queues its copy on cuda_sync.stream before enqueue returns, so later writes that the caller queues on that same stream are ordered after the copy. To overwrite the source buffer from any other stream, the caller records its own event on cuda_sync.stream after enqueue returns and makes that other stream wait on the event first; successful admission alone does not make unordered cross-stream reuse safe.

A column with no rows has null data and zero byte_offset; the library ignores its stride values, so a producer may report any (NumPy reports 0).

Every input column, CPU or CUDA, follows one layout rule, so that one array helper serves batches and publications. Strides count elements. A null strides pointer means compact row-major, as DLPack before 1.2 allowed. Any nonnegative stride is accepted: a slice such as a pose array’s first three columns, every k-th row, padded rows, column-major order, or a zero stride that repeats one value; a dimension of extent one ignores its stride. A negative stride, or a column whose last element’s address overflows, returns INVALID_ARGUMENT, and ovspatialquery_get_last_error() names the column and the rule. A CPU batch plan reads strided columns in place. Elsewhere the library reads a compact column in place and copies any other into compact storage of its own, whatever its ownership; the copy is charged like a COPIED_ON_SUBMISSION copy and, on CUDA, runs on cuda_sync.stream after its wait event. The caller still keeps a borrowed column unchanged until the operation is terminal.

enum ovspatialquery_ordinal_selection_kind_t#

HEAD and RETAINED_EXACT name completed publications, so a reader never sees work that may still fail. A GPU producer that publishes every step would otherwise have to wait on the host for each publication before it can enqueue the queries that read it. ADMITTED_EXACT lets a CUDA plan launch or a CUDA pair reporter advance name a publication that has been admitted and is still being prepared on its device: the work is ordered after the publication on the device and the host waits for neither. If that publication fails, the launch completes with OPERATION_FAILED and its rows carry the FAILED status with zero hits; the advance completes with OPERATION_FAILED and writes the FAILED outcome to its device counts. The head and the retained window are unchanged by either outcome. Once the library has observed the failure, the ordinal is neither retained nor pending: a later ADMITTED_EXACT selection of it returns ORDINAL_NOT_RETAINED at admission and an update based on it returns ORDINAL_MISMATCH (NOT_READY when it was the first set), so the producer publishes again on the head, or sets the population again when the failed publication was its first set. Work enqueued while the failure is in flight gets either outcome.

Exact queries evaluate stored surfaces rather than only their bounds. The implementation chooses arithmetic precision and acceleration; input or output dtypes do not prescribe intermediate precision. Local mesh vertices use float32 while world placement retains double precision. Results near edges, touching surfaces, or ill-conditioned geometry can differ between implementations. No universal numerical error bound is promised. Identity, filtering, clipping, and each query family’s result semantics still apply.

Input domain. The CPU evaluators run in float inside each object’s local frame, so the library bounds what it accepts to keep every value it hands them finite. Every coordinate, half extent, radius, distance, and contact_tolerance a caller passes, every local vertex coordinate, half extent, and radius of a stored definition, and every published object’s world AABB lies within +/-2^60 caller units; every uniform placement scale lies within [2^-60, 2^60]. Outside it the input is malformed: a synchronous call or plan creation returns INVALID_ARGUMENT, a batch row reports BATCH_ROW_INVALID_ARGUMENT, and each source adapter states where it refuses a definition or an object. The bound is in caller units, so a stage in centimeters reaches it at a smaller physical size.

Room for two optional per-query inputs without a layout change. Null means absent. A non-null entry returns NOT_SUPPORTED and the query has no effect, so a caller that sets an input this library predates fails cleanly.

contact_tolerance is a geometric expansion in caller units: a ray tests a tube of this radius; a sphere sweep and sphere overlap add it to the sphere radius; an AABB expands each face by it; and an oriented box expands its local half extents by it before its pose is applied. Pair operations in ovspatialquery_pairs.h use their stated expanded-AABB predicate. Tolerance never changes stored geometry.

Ray and sweep distance intervals are closed: the first contact is the least distance in [min_distance, max_distance] at which the ray point or moving shape touches stored geometry. Stored spheres, boxes, capsules, and convex hulls are solid, so clipping the start of a path behaves like moving its origin there: a point or shape already touching or overlapping one at min_distance reports that object at min_distance. The exact contact of such a ray or sphere is the stored surface point nearest its center, with the outward normal there. Triangle meshes are surfaces: a ray inside a closed mesh reports its next crossing, and a sweep already touching a triangle it does not ignore reports it at min_distance.

A triangle’s front normal n is (v1 - v0) x (v2 - v0). A single-sided triangle stops a ray only through its front face. A sweep ignores a single-sided triangle whose front normal points along the motion, so a shape resting on a floor can leave it: a sphere sweep one with n . d > 0, a box sweep one with n . d >= 0, where d is unit_direction, as PhysX’s own sweeps decide. A box moving parallel to a single-sided triangle therefore ignores it, and a sphere does not. A sweep meets every other triangle as a two-sided surface: its first contact is where the shape first touches the triangle’s face, an edge, or a vertex, from either side, including a contact at min_distance with the shape’s center behind the triangle. Double-sided triangles are never ignored.

OVSPATIALQUERY_QUERY_MESH_BOTH_SIDES in a query’s or a batch launch’s query_flags lets every triangle count from both sides. A ray also crosses back faces. Its normal is the triangle’s front normal on a single-sided mesh, as PhysX reports it, so n . d > 0 marks a back-face hit; a double-sided mesh still reports the normal facing the ray. A ray with a nonzero contact_tolerance reports its contact normal there mirrored across the triangle’s plane to the front side, which on the face is the front normal. A sweep ignores no triangle, so a shape resting on a floor and moving up reports it at min_distance; its normal is unchanged.

Device-neutral batch column contract.

Q is common.query_count, C is common.hit_capacity, and H is the terminal stored_hit_count. Reservation payload tensors have capacity shapes based on C. A successful typed fetch returns payload tensors with exact shapes based on H. Hit-range tensors always use Q or scalar shape as documented.

The library copies every returned DLTensor descriptor value into the caller-owned output struct. Data storage and the shape and strides arrays stay operation-owned. Reservation metadata arrays and fetched-result metadata arrays are separate immutable snapshots that remain valid and unchanged until the operation is destroyed.

For each required or requested payload column, reservation and fetched descriptors refer to the same backing storage. Their data, dtype, device, strides, and byte_offset values are equal. Only shape[0] changes from C to H; later dimensions do not change. A CUDA consumer can therefore enqueue from reservation descriptors and wait on common.result_ready without a later relocation invalidating its arguments.

DLPack dtype, rank, shape, strides, device, and byte_offset are authoritative. Every present tensor uses common.execution_device, except under HOST_MAPPED below. CPU contents are unreadable while the operation is pending, and all columns share readiness, failure, and lifetime. Separate descriptors do not imply separate allocations: published columns use fixed per-dimension element strides, while backing allocation, internal packing, and any projection are implementation details.

An optional unrequested tensor is an all-zero absent descriptor; callers can test shape == NULL. Every present result tensor has ndim >= 1, non-null shape, and its documented dtype. A required or requested tensor with no terminal hits is present with shape[0] == 0. Object IDs and hit-range tensors are always present.

Every present payload column except the triangle payload below is valid for every stored hit. A provider cannot leave per-hit holes in such a column.

Geometry types and values are present or absent together, as are the exact feature columns. Within a present feature group, kinds[i] == NONE leaves that row’s source face, source corners, and barycentrics unspecified, so a consumer must mask those columns by kinds; kinds[i] == TRIANGLE makes its source face, three source corners, and barycentrics valid. Candidate plans reject SOURCE_FEATURE. This semantic tag replaces the former generic per-hit validity bitmap.

common.truth selects the candidate or exact union arm. C cannot prevent a caller from reading the wrong arm; the tag and distinct field names make the validity rule explicit. Candidate contact columns describe only the published AABB proxy, while exact contact columns describe the stored surface. QUERY_POSITION is accepted only by sphere sweep and is the moving sphere center at contact.

On terminal success, successful nonempty ranges are pairwise disjoint and densely cover [0,H), with no overlap or gap. Their order need not match query order. Every offset + count is at most H, and H is at most C. A miss has count zero. A non-success query row has zero offset, count, and truncation and no payload. truncated[i] is nonzero exactly when a match was omitted by that query’s semantic limit or remaining capacity. A truncated raycast or sweep keeps its nearest matches by distance, then object ID, so CPU and CUDA plans store the same set, except which of one object’s mesh crossings at exactly the cut-off distance stay; order within a range is unspecified. Reserved storage in [H,C) is unspecified and is outside every fetched payload shape.

A recoverable CUDA operation-level failure publishes a safe empty device result before signaling result_ready: stored_hit_count is zero; every query status is BATCH_ROW_FAILED; and every offset, count, and truncation value is zero. No payload row is readable. DEVICE_LOST makes no such storage or event guarantee.

A CUDA plan created with HOST_MAPPED in result_fields keeps every column of every result slot in page-locked host memory mapped into the plan’s device, so a host reader reads in place instead of copying. Each present tensor reports { kDLCUDAHost, 0 }; its address is valid on the host and on common.execution_device, which stays the plan’s CUDA device. The device writes every column, including the safe empty result above, before result_ready, and the host may read once result_ready has completed: a wait, status poll, or typed fetch that observes the terminal state implies it. Launch, stream, wait-event, and ordinal rules are those of any CUDA plan. Plan creation charges the mapped columns to the instance’s host_byte_budget (HOST_BUDGET when they do not fit) and the plan’s device working storage to the device budget.

Implementation note: the plan computes on device storage as without HOST_MAPPED, then one pass behind the launch copies each column into mapped memory as one contiguous run, the payload columns sized from H on the device, because scattered device stores to host memory cost several times more than pageable copies.

Exact plan admission rejects an unsupported device, family, or precision. After admission, mandatory built-in geometry cannot produce NOT_SUPPORTED and CUDA execution never falls back to CPU. A binding projects these tensors directly and retains the operation until all consumers finish.

Reusable batch-query functions#

Batch workflow (error handling omitted):

create_*_plan(instance, &plan_desc, &plan);
queued = enqueue_*_plan(instance, plan, &batch, &reservation);
wait_op(instance, queued.op_id, timeout, &wait_result);
fetch_*_batch(instance, queued.op_id, &result);
// Read result.columns. CUDA consumers first wait on result_ready.
destroy_op(instance, &queued.op_id);
destroy_batch_plan(instance, plan);

A plan fixes one family, target, device, capacities, and result slots. Each launch selects an ordinal and supplies rows only for that family. Each result uses the same semantic DLPack columns on CPU and CUDA. Tensor device metadata identifies where the column lives.

A successful enqueue writes one immutable reservation snapshot and never retains or later modifies that caller-owned struct. While pending, callers may inspect reservation metadata and storage descriptors but may not read CPU contents. CUDA callers may enqueue downstream work from the reservation tensors and event without a host wait. Typed fetch returns terminal tensor shapes on either device. Fetch is repeatable and non-consuming; it returns NOT_READY while pending. It returns OPERATION_FAILED after terminal failure and preserves its output, because a failed operation has no fetched payload result. After recoverable CUDA failure, only the documented safe empty reservation hit ranges are readable.

Asynchronous operation functions#

ovspatialquery_result_t ovspatialquery_wait_op(
ovspatialquery_instance_handle_t instance,
ovspatialquery_op_id_t op_id,
ovspatialquery_timeout_t timeout,
ovspatialquery_op_wait_result_t *out_wait
)#

Waits until an operation is terminal or timeout expires. Zero polls; TIMEOUT means this call observed pending work, not operation failure. TIMEOUT_INFINITE waits until a terminal state. A timeout is not cancellation: the operation and all input-lifetime obligations remain live. A caller CUDA wait event must eventually resolve; a permanently unsignaled event violates the caller contract. Detected device loss ends the affected work with a terminal DEVICE_LOST failure.

On either terminal state this function returns SUCCESS and writes the state; query_op_status supplies the machine-readable terminal cause. Returning a terminal state marks it observed, which is required before destruction.

ovspatialquery_result_t ovspatialquery_query_op_status(
ovspatialquery_instance_handle_t instance,
ovspatialquery_op_id_t op_id,
ovspatialquery_op_status_t *out_status
)#

Polls operation state and approximate progress without consuming it. Returning a terminal state marks that terminal state observed. A typed fetch also observes a terminal state when it returns success or OPERATION_FAILED; a pending fetch that returns NOT_READY does not.

ovspatialquery_result_t ovspatialquery_destroy_op(
ovspatialquery_instance_handle_t instance,
ovspatialquery_op_id_t *inout_op_id
)#

Destroys a terminal-observed CPU operation or terminal-observed operation with no returned CUDA views. Pending or terminal-unobserved work returns BUSY. Success writes INVALID_OP and releases borrowed inputs/results. Use destroy_op_after_cuda for every CUDA operation with returned device views, whether it ended in success or a recoverable failure. A HOST_MAPPED plan’s launch may use either: this function when no device work the caller queued still reads its columns, because a terminal state implies the library’s own device work is done.

ovspatialquery_result_t ovspatialquery_destroy_op_after_cuda(
ovspatialquery_instance_handle_t instance,
ovspatialquery_op_id_t *inout_op_id,
ovspatialquery_cuda_event_t *inout_consumer_done
)#

Retires a terminal-observed CUDA operation after consumers.

inout_consumer_done is one caller-owned event covering every consumer of the result views. Success transfers and zeroes the event, invalidates the op ID, and lets the implementation release result storage when device-safe. A recoverable terminal batch failure still signals result_ready after it writes the safe empty hit-range state documented above. Consumers can observe that state and safely join consumer_done before storage retirement. OVSPATIALQUERY_API_DEVICE_LOST is terminal, but does not promise usable CUDA result storage, a ready event, or normal consumer-event retirement. CPU operations, pending operations, and terminal states not yet observed through wait, status, or typed fetch are invalid.
